# 信息雷达 · 企业微信推送：消息类型、触发条件、推送时机与展示格式

> 生成时间：2026-11-15 23:05（北京时间）
> 适用范围：投资工作台 `wt.likeke.top` + 本机「信息雷达 / 工作台联动」
> 拍板结果（用户 2026-11-15）：**走信息雷达通道** + **止损 / 跟单清仓 / 趋势跌破三类全算 P0 且都 @all** + **仅交易时段 60 秒轮询**

## 一、一句话结论

信息雷达原有的企业微信群机器人通道保留不变，新增「做T信号」「今日决策卡」两类消息，并把「跌破止损 / 跟单组合已清仓 / 跌破大趋势线」做成 **P0 即时高优先级通知**：绕过 5 分钟合并与 4 秒节流、直发并 `@all`，在队列层、格式层、时机层三个层次与普通推送区分。现有资讯 / AI 精选 / 日报（P3）**一字未改**。

## 三、消息类型总表（触发条件 / 推送时机 / 展示格式）

| 级别 | 消息类型 | 触发条件 | 推送时机 | 展示格式 |
|---|---|---|---|---|
| **P0** | 紧急·三类预警 | 持仓**现价 ≤ 止损价**（公开源实时价补算，与 `/api/alerts.hit_stop` 同口径，级别 `stop`）；或 `cleared` 跟单组合已清仓；或 `trend` 有效跌破长周期均线。三者**任一新出现或级别变化**即触发 | **检测到即刻直发**，不等队列、不等 5 分钟合并、不等 4 秒节流；同一交易日同标的同级别只提醒一次；级别变化立即重推；`stop` 真恢复后再次破位算新事件可再推；`holds_ok=false` 时跳过，避免旧价误报 | 企业微信 `text` + `mentioned_list:["@all"]`；首行 `🚨【P0 紧急 · N 条】HH:MM:SS`；多条**合并成一条**消息，逐条列 名称(代码) / 级别 / 现价 / 止损价 / 浮盈亏 / 原因；末尾附处理入口与去重说明 |
| **P1** | 做T信号 | `t_signal.json` 中某持仓 `signal` **新进入** `buy` / `sell`（沿用工作台 `_SEEN_TSIG` 口径）；离开信号后再次进入可重推；快照 `stale=true` 时不推 | 状态变化即时入队（雷达发送线程 2 秒轮询，实测 2–4 秒内发出）；同标的同信号 1 小时冷却 | 普通 `text`，**不 @人**；首行 `【P1 做T信号】N 只新出现可操作信号`；逐条「高抛/低吸 名称(代码) 强度X 空间X%｜参考价 →」；附数据时间与「强信号低吸已按 v2 硬过滤」说明 |
| **P2** | 今日决策卡 | 三档（必须今天做／可以等／只是观察）任一有内容 | **每交易日 09:25 推一次**；结论发生实质变化时 **15:10 补推一次**；非交易日不推；同日同时点只推一次（`identity` 唯一约束） | 普通 `text`，**不 @人**；首行 `【P2 今日决策卡】日期 · 盘前/补推`；分三段，每档最多 4 行，缺字段显「—」；末尾标注「推送版决策卡由服务端只读数据汇总，与网页版同源但非逐字复刻；不代下单」 |
| **P3** | 现有提醒 | 保持原有逻辑不变：新资讯、AI 精选、源恢复、AI 日报 | 5 分钟合并发送 / 日报生成后 / 测试消息即时 | **格式完全不变**，无优先级前缀、无 @all |
| — | 链路测试 | 手动执行 `python push_bridge.py --test` | 即时 | 普通 `text`，标注「链路测试」，**不 @all** |

### 优先级如何「区分」（三个层次同时生效）

1. **队列层**：P0 完全不进 `wecom_jobs`，由桥接器直接调企微接口 → 零排队；P1/P2 进雷达队列，由雷达统一发送、重试、计入状态页。
2. **格式层**：只有 P0 带 `@all` 强提醒 + `🚨` 前缀；P1/P2 带普通级别前缀；P3 无前缀。
3. **时机层**：P0 即时 → P1 状态变化 → P2 定时 → P3 合并。

## 五、去重、冷却与安全闸门（这一版特意加固的地方）

| 规则 | 说明 |
|---|---|
| **首次运行静默播种** | 启动时若发现存量预警（本次上线时线上有 **7 条**：3 清仓 + 4 趋势跌破），全部记为基线、**不补发历史消息**，否则首启会连发 7 条 @all 刷屏。当日决策卡两个时点也标记为已处理，次日起正常推 |
| **当日同级别一次** | 原方案写的是「同级别 1 小时冷却」。实测发现 `trend` 信号来自 **1 小时 TTL 缓存**（22:39 有 4 条，22:52 缓存过期全部消失），按冷却推会在缓存每次刷新后「消失→重现」并稳定每小时 @all 一次。故改为**同一交易日同标的同级别只提醒一次**，跨日重新计数 |
| **级别变化立即重推** | `stop → cleared`、`cleared → trend` 等变化绕过当日去重，立刻推 |
| **stop 真恢复可再推** | `stop` 是价格实时判定，标的回到止损线上方后再次破位算新事件，当日允许再推；`cleared` / `trend` 属状态型，恢复时保留当日记录以防缓存抖动 |
| **合并发送** | 同一轮多条 P0 合并为一条消息、只 @all 一次；超长文本由 `chunks()` 分段，仅首段 @all |
| **失败不记去重** | 企微未受理（`retry` / `failed`）时不写去重键，下一轮继续重试；成功才记录 |
| **休市静默** | 交易日判定用引擎 `market_status()` 的 A 股节假日表（比本机 weekday 准）；本机仅在 09:00–15:30 每 60 秒轮询，非交易时段直接睡到下个交易日 09:00 |
| **数据可信闸门** | `brief.holds_ok=false`（持仓读取失败）或 `t_signal.stale=true` 时不推对应消息，避免用旧数据误报 |
| **凭据** | 令牌只存本机 `工作台联动/config.json`，webhook 只存本机 `信息雷达/data/preferences.json`；两边都做 URL 白名单校验，不写日志、不回显；线上接口复用既有 `RADAR_TOKEN` 与 ±15 分钟防重放 |

### 立即生效方式（需要你做一步）

当前 WorkBuddy 沙箱会话内启动的后台进程会在会话结束时被清理：实测用内置 `python.exe` 与系统 `pythonw.exe` 各拉起一次，两次日志都正常写入「进入常驻推送模式 / 非交易时段静默」，但新会话复查时进程均已消失；而**你桌面会话里**启动的 `radar_sync` 常驻进程（PID 32744）一直存活。代码与链路本身无问题，差异在进程归属的会话。

因此要让推送真正 7×24 常驻，请在自己的桌面会话里拉起一次：

- **立即**：双击 `D:\我的工作台\工作台联动\一键启动工作台.bat`（或运行 `python start_services.py`）。它会幂等拉起 TSP、信息雷达、同步循环、**企微推送桥接器**四者，并用 `push_bridge.pid` 防重复启动。
- **下次登录自动生效**：注册表 Run 项 `InvestWorkbenchServices` 已安装，指向 `start_services.py`；桥接器已接入其第 4 步，登录即自动拉起，无需重复操作。
- **确认方式**：`工作台联动/push_bridge.log` 出现「进入常驻推送模式」，或任务管理器里出现带 `push_bridge.py` 命令行的 python 进程。

## 八、已知边界

1. **实时性**：P0 依赖本机每 60 秒轮询 + 公开源行情刷新，最坏约 60 秒延迟；不是交易所逐笔推送。若需秒级，需改成长连接或服务器侧主动推，属另一套架构。
2. **依赖本机开机与启动器**：桥接器跑在本机，关机、或尚未双击「一键启动工作台」期间不会推送；线上工作台不代发。注册表自启项已在，下次登录会自动拉起。
3. **trend 信号 TTL**：来自工作台 1 小时有效期的 `trend_signal.json` 缓存，缓存过期会暂时消失；已用「当日一次」去重防止反复 @all，但趋势信号本身不是持续监控。
4. **企微限流**：群机器人约 20 条/分钟；P0 已合并发送 + 当日去重，P1/P2 低频，正常情况下不会触发；`send()` 对 `45009` 有 `retry` 处理。
5. **决策卡口径**：推送版与网页版不同口径处已在消息正文标注；「可以等」取跟单共识票快照前 2，网页版取 `recBuyRows()` 带预算与手数的完整清单。
6. **不代下单**：所有消息只做信息整理与关注提示，不含买卖指令、仓位或涨跌预测。
