二、性能瓶颈（按严重度标注）

环节证据（实测/静态）严重度成因与影响
首屏加载index.html 1,062,597 B，gzip 后实测 326,156 B / 0.16s（nginx gzip on）中单文件无代码分割；每次版本更新整包失效，sw 需 v97→v98 全量 bump
启动链路boot() 顶层约 15 个串行 await（baseline/trades/health/session/restore/names/poolcfg/serverCodes/cached/holdings/config/backfill/market/perf/recs/swing/etf/valuation…）高RTT 串行累加；任一慢接口拖慢整体 ready，虽有 safeLoad 隔离但不并行
渲染refreshAll() 一次调用 26 个 render* 函数；DOM 1438 div / 606 id / 647 内联 style；4 canvas 手绘高隐藏页也重绘；60s 行情轮询每次触发全量刷新；无虚拟列表
数据读取server.py _json_load() 每次 open+json.load 全量解析：last_snapshot.json 3.43MB、strategy_lab.json 3.11MB、blog_items.json 1.38MB 等；data 目录 170 个 JSON / 27.13MB高无 ETag/304、无进程内 TTL 缓存（仅 _BT/_FV 等局部缓存）；重复请求 CPU 浪费
并发根服务 ThreadingHTTPServer + daemon_threads，无连接数上限；引擎批量 ThreadPoolExecutor max_workers=6，抓数 max_workers=2中线程无节制创建；上游雪球风控迫使 12只/批+45s 冷却，推送必须 TAT 分片
缓存一致性sw.js 手写 cache-first/网络回填；ASSETS 预缓存 7 项；API Cache-Control: no-store中版本 bump 全量换缓存；曾出现旧 HTML 外壳 + 新数据的错位（v98 修复）
轮询持仓 15s、行情 60s、跟单 120s、做T 5min、告警 2min、全量刷新 5–120min(可配)中有页面可见性/交易时段闸门，设计较好；但 refreshAll 范围过大放大每次轮询成本
资源占用服务进程 VmRSS≈154MB / Threads=2（systemd MainPID）；nginx worker_processes auto, worker_connections 768低-中单机够用；数据量增大后全量 JSON 解析会推高内存与 GC
回测strategy_lab 3 池 × 25 策略 × ~1250 日窗口，上次 elapsed=138.6s；每月 1 日 04:30 timer中纯 Python 逐策略循环；可接受但向量化/并行仍有明显空间

三、GitHub / 全网同类高性能方案对标

检索顺序：先 GitHub（ stars / 最近推送由 GitHub API 于 2026-11-18 核验），结果不足再扩展到全网公开仓库与官方文档。风险分级以「当前单文件 SPA + Python 标准库后端 + 上游风控代理抓取」这套约束为基准。

uPlot
10,651★ · 最近推送 2026-11-17（GitHub API 核验）
原生 canvas 时序折线/面积/OHLC，正好对应核心池净值双图与几何超额图面向大点数时序的轻量 chart；官方 benchmarks 目录提供与主流图表库的渲染耗时对比，库体积显著小于 ECharts
依据：官方 README / benchmarks 目录（结构性优势：只画可见像素、单 canvas、无 DOM 节点）
首屏净值曲线、业绩页区间图；需要保留单文件内联以 UMD/内联形式 A/B 替换 4 个手绘 canvas；先只换净值曲线，保留原绘制函数作回退；DPR 适配可沿用现有代码需谨慎接入
成本：中：改动集中在 2 个渲染函数，但需重做交互与令牌配色映射，sw 需 bump

四、整体评测

  • 功能覆盖度：优秀 — 20 页签覆盖选股、持仓、条件单、估值、业绩、情绪、回测、雷达、账本、ASR 等完整投资闭环；多数页面有明确降级/口径提示，数据真实性约束强（不编数）。
  • 架构一致性：良好但耦合重 — parts 构建链、契约测试、令牌化主题、PWA 独立页分流等约束清晰；代价是 517 个全局函数、单文件 1.04MB、4 script/3 style 硬契约，任何局部优化都要全量重建。
  • 加载性能：中等 — gzip 后 326KB / 0.16s 传输并不慢，真正耗时在启动 15 步串行请求与随后的全量渲染；PWA 让二次访问更快，但也引入过缓存错位。
  • 渲染效率：偏弱 — refreshAll() 26 个渲染函数无差别执行、隐藏页照画、无虚拟列表、canvas 手绘；这是当前最值得改的部分。
  • 资源与并发：够用但有上限 — 单进程 ~154MB、2 线程；ThreadingHTTPServer 无连接上限，大 JSON 每次全量解析；上游风控决定抓取只能代理+分批，短期不要推翻。
  • 维护状态：活跃 — 服务端 7 个 systemd timer + 本机 15 个自动化（净值 7、持仓 8）在跑；本次评测时全链路均正常。
